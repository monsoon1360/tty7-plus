<kbd>Ctrl 4</kbd> opens a panel on the right of the window. It is hidden by
default; whichever tab you leave it on is where it opens next time.

The two tabs at the top select **Source Control** or **Files**. Source Control
is the default. <kbd>Ctrl 4</kbd> or the panel tile puts the panel away; its
width animates over 140 ms. Saved Info or GitHub choices open Source Control
without resetting other settings; the former Search choice opens Files.

## Files

A file tree rooted at the pane's working directory, with git status decorations
on every row and a search box at the top. The search box carries a clear button
while there is something in it. The eye in the panel's title bar — or **Show
Dotfiles** in a row's right-click menu — lists dotfiles and dot-directories,
and the choice is remembered across launches.

- **Click a file** to open it in the built-in editor.
- **Drag a file out** to Finder or Explorer to copy it there.
- **Drag files in** from the desktop to copy them into the folder under the
  cursor. A folder row takes them itself, a file row stands in for the folder
  holding it, and the empty space below the tree means the top of it. Folders
  come in whole, the executable bit survives, and a name that is already taken
  is asked about rather than replaced.

Both directions work over a [remote workspace](/remote/workspaces) too, reading
on one machine and writing on the other, up to the size one control frame can
carry — past that the panel tells you to use [SFTP](/remote/sftp).

### Find in files

The Files field filters file names and searches content across the project:
the repository root of each pane in the tab, or its directory outside a repo.
**Right Panel: Search** in Search Everywhere, or the `ShowRightPanelSearch`
action, opens Files and focuses this field. Search is not a separate panel tab.

Results arrive as you type, grouped by file with a count per file; click a
file's row to fold it away. Each hit is its line with the matches highlighted,
and **clicking one opens the file in the built-in editor with the cursor on that
line and column**. <kbd>Enter</kbd> in the field searches again, for when the
files changed underneath you.

The three toggles at the end of the field:

| | |
|---|---|
| **Aa** | Match case — off by default, so `needle` finds `Needle` |
| **ab** | Whole word — `foo` no longer finds `foobar` or `foo_bar` |
| **.\*** | Regular expression, in Rust [`regex`](https://docs.rs/regex) syntax. A pattern that does not parse says why in red instead of searching |

What is searched is what the tree shows: a folder's `.gitignore` applies whether
or not it is in a repository, and dot-files and dot-directories are skipped.
Binary files and files over 1 MB are stepped past. A search stops at 2,000
matching lines, 100 per file, 20,000 files or ten seconds, whichever comes
first, and says so under the results — narrow the query to see the rest.

In a [remote workspace](/remote/workspaces) the search runs on the remote
machine and only the hits cross the network. A remote `tty7-server` older than
this feature cannot search; the tab says so and asks you to update the server
rather than showing an empty result. An SSH pane's files are browsed over
[SFTP](/remote/sftp), which cannot search them — open the host as a remote
workspace for that.

## Source Control

The git panel for the focused pane's repository, in four groups — **Merge
Changes**, **Staged Changes**, **Changes**, **Untracked**. Write a message,
commit, and push without leaving the window.

[Source control →](/git/source-control)

## The editor

<kbd>Ctrl 3</kbd> toggles the code panel; clicking a file in the Files tab opens
it there. It is a real editor — syntax highlighting, line and column readout,
wrap toggle, and a Markdown preview — meant for the edit you would otherwise
have opened `vim` for.

| | |
|---|---|
| <kbd>⌘ S</kbd> | Save |
| <kbd>Esc</kbd> | Back to the terminal |

The four regions are <kbd>Ctrl 1</kbd> (sidebar), <kbd>Ctrl 2</kbd> (the
terminal area), <kbd>Ctrl 3</kbd> (this editor) and <kbd>Ctrl 4</kbd> (the
right panel). <kbd>Ctrl 2</kbd>, <kbd>Ctrl 3</kbd> and <kbd>Ctrl 4</kbd> are
<kbd>Ctrl</kbd> with a digit, not the macOS <kbd>⌘</kbd>: they are window
chrome, and on the other side of them the shell no longer receives NUL, ESC and
FS. Every one of the four animates its width as it appears or disappears. Any
of them is a line of `config.json` away from a different chord.

Files are watched on disk: a change underneath you is picked up, and closing
with unsaved edits asks before discarding them. Files over 4 MB and anything
that looks binary are refused with a note rather than opened badly.

### Where it opens

The editor docks beside the terminal, taking half the space between the sidebar
and the right panel. The terminal keeps running, stays visible, and stays
typeable — click it, read what your agent said, click back. Diffs open in the
same column.

Drag the divider for any width between a fifth and four fifths of that space —
the range `document_ratio` keeps — or double-click it to cycle a third, a half
and two thirds. **Document: Third / Half / Two-Thirds Width** in Search
Everywhere do the same. On a narrow window the terminal's own floor stops the
divider sooner.

Choose **Settings → General → Editor → Document layout** to **Dock beside
terminal** or **Fill window**. The choice is global: existing and new tabs,
all open windows, and the next app launch use the same layout. The divider's
width persists as `document_ratio`.

A window too narrow to give both the terminal and the document a readable width
fills for that file only — widen it and the column comes back, without your
setting having changed.

## Choosing the editor

**Settings → General → Editor → File open method** decides what a file picked
in the file tree, in quick open or in a search result opens in:

| Method | What happens |
|---|---|
| **Built-in editor** | The column above. The default. It shows one file and names it in the status bar at its foot. |
| **Helix** | The same document region running `hx <path>` — `hx <path>:<line>:<column>` from a search hit. |
| **Vim** | The same document region running `vim <path>`, or `vim +<line> <path>` from a search hit. |

All three methods share the document region, its Dock/Fill layout and 140 ms
open/close animations. The region shows no file name of its own: Helix and Vim
put it in their own status line, and the built-in editor puts it in its status
bar.

One file is on screen at a time. Opening another file **replaces** the file the
built-in editor shows; with Helix or Vim it is handed to the session already
running in that terminal, so those editors keep their buffers and their own way
of switching between them (`gn`/`gp`, the buffer picker). Helix and Vim have one
dedicated backing session per terminal, not extra Terminal rows in the sidebar
or terminal switcher, and their processes start in the current terminal's
directory. Opening a file focuses the editor; a line from a search hit with
Helix sends `:goto <line>` to the running session.

Opening a file puts keyboard focus in its editor. On macOS, Helix and Vim also
select the user's last ASCII-capable keyboard layout so modal commands do not
start an IME composition.

**Ctrl+2** focuses the terminal, hiding a document that fills it; **Ctrl+3**
toggles the shared editor region. In Dock mode both can remain visible and
typeable. Editor selection and launch arguments survive app relaunches. A
terminal is never hidden while it is the only content in the workspace.

Files on a remote host always open in the built-in editor: `hx` and `vim` are
programs on this machine, and the file is not. The setting covers the file
tree, quick open and search results only — a link in the terminal grid follows
**File links in the grid**, and source-control changes, the SFTP browser and
the problems list open in the built-in editor, which can honour a line and a
column on either machine.
